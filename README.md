- **2.0.3** — A second, worse real performance bug, found the same way as v2.0.2 — a real Phase 2 run that had now been going for 7 hours (well past even the unfixed clustering bug's worst case), with only a single unrelated `scipy` warning printed after 13 minutes on a fresh attempt. Read `geometry.py`'s `find_regions()` (shared by `spot.py` and `stripe.py`) proactively rather than waiting on another failed run: it called `np.where(labeled == label_id)` once per connected component, and each call re-scanned the *entire* image array, not just that component. - **2.0.2** — Real performance bug, found because Phase 2's real run against Phase 1's output was still going after an hour with zero progress output — `pattern_extractor/clustering.py`'s `fit_reference()`/`assign_clusters()` fed *every* masked-in pixel into `scipy.cluster.vq.kmeans2` (100 iterations), with no subsampling at all. Benchmarked: a 2-million-pixel fit took ~18s; across ~920 real images that's consistent with a run stretching well past an hour. Fixed: the iterative fit now runs on at most `max_pixels_for_fitting` (default 50,000) randomly-sampled pixels — checked to reproduce a full 2-million-pixel fit's centres to within ~1 RGB unit, in about 1/100th the time — then every actual pixel is assigned to the fitted centres in a single vectorized pass (`scipy.cluster.vq.vq`, not iterative), so `fractions`/`label_image()` still reflect the whole image, not just the fitting sample. Also added per-species progress logging to `PatternExtractorPipeline.run()` (`[n/64] <species>: <count> processed`) and had the Phase 2 notebook configure logging visibility before running — this stage previously gave zero indication of progress, making a genuinely slow run indistinguishable from a hung one. 1 new test (confirms subsampled fitting still labels every real pixel) — 119 tests passing, ruff clean.

## Research Question

**Is visual pattern similarity among surgeonfish (family Acanthuridae) genetically associated with evolutionary relatedness — or does it arise independently of shared ancestry?**

Concretely: for a set of Acanthuridae species with a known molecular phylogeny, does quantified visual similarity (color pattern, texture) between species pairs correlate with their phylogenetic distance? A significant result (tested primarily via Kmult, a multivariate phylogenetic-signal statistic, with a distance-based Mantel test as a secondary check — see Planned Approach) is evidence that visual pattern covaries with phylogenetic relatedness — closely related species tend to look more alike than distantly related ones do. A null result means visual pattern is not explained by relatedness at the level these methods can detect, and any resemblance between species is more likely convergent.

**What this test cannot, on its own, distinguish**: pattern covarying with phylogeny is consistent with pattern being heritable, but it's equally consistent with pattern tracking an ecological variable (diet, depth, reef zone) that is itself phylogenetically conserved — closely related surgeonfishes tend to share ecology, not just genes. Kmult/Mantel alone cannot separate "inherited" from "conserved-ecology-mediated" as the reason for a significant result. Testing that distinction specifically would require ecological covariates (e.g. from FishBase) and a phylogenetic-regression approach (`procD.pgls`) — not yet in scope, noted here so the claim this project can support isn't overstated.

This is a correlational test, not a claim of direct causation: both statistics establish association between visual pattern and phylogeny. Neither, on its own, identifies the underlying genetic or developmental mechanism, or separates heritability from conserved ecology.

(An earlier draft of this table used raw NCBI Taxonomy species-rank counts, which include those hybrids/placeholders as if they were extant species — that inflated every genus's denominator and understated coverage; e.g. *Ctenochaetus* looked 69% sampled and was actually fully sampled. Missing species were dropped for image availability (Phase 0), not by design — this is a real limitation, not a curated subsample.

A key biological complication: *Acanthurus* is paraphyletic with respect to *Ctenochaetus* in the molecular phylogeny — Sorenson et al. (2013) recover the paraphyly specifically as *Ctenochaetus* nested with two named *Acanthurus* species, *A. nubilus* and *A. pyroferus*. Whether that paraphyly is also reflected in visual similarity is one specific, checkable prediction of the broader research question above, and both named species are confirmed present in the 50-species phylogeny-matched set below (`data/phylogeny/species_coverage.csv`), so the prediction is testable as named, not just as a genus-level proxy. Sorenson et al. recommend dissolving *Ctenochaetus* into *Acanthurus* on this basis; this project keeps them as separate genus labels (standard reference-database convention) since genus is a descriptive grouping here, not part of the statistical test itself, which operates at the species-tip level. One caveat worth flagging here rather than only in the phylogeny paragraph below: restricting to genetically-sampled species drops *Acanthurus* coverage from 79% (31/39) to **54% (21/39)** — the lowest of any genus post-restriction, and the genus this specific prediction most depends on being well sampled. The two species the prediction actually names are both present, but the wider *Acanthurus* context around them is thinner than the pre-restriction number suggests.

The molecular phylogeny used as the evolutionary-relatedness reference comes from the Fish Tree of Life (fishtreeoflife.org, Rabosky et al. 2018, *Nature* 559, 392–395), specifically its **genetic-data-only tree** (not the "complete" tree, which places species lacking genetic data via stochastic polytomy resolution — a taxonomy-conditioned random draw, not phylogenetic signal; see `data/phylogeny/README.md` for the full reasoning, source, and a checksum for reproducibility). **50 of the 64 study species (78.1%) have real genetic-data placement** in that tree (49 by exact name match, 1 — *Zebrasoma veliferum* — via a confirmed taxonomic synonym, cross-checked only against NCBI's synonym table so far — see `data/phylogeny/README.md` for the standing caveat on that); the analysis is restricted to those 50. The 14 still unmatched are concentrated in *Acanthurus* (10 of 14; already the best-sampled genus pre-restriction) rather than compounding the *Naso*/*Prionurus* sampling gap above — most have GenBank sequence data that simply wasn't part of this tree's fitted supermatrix, not an absence of genetic data altogether; see `data/phylogeny/species_coverage.csv` and `README.md` for the full per-species breakdown and reasoning. ("Nine molecular loci" describes a different, Acanthuridae-specific timetree — Sorenson, L., Santini, F., Carnevale, G., & Alfaro, M. E. (2013). ## Data Sourcing & Compliance

Images are collected programmatically via `src/dataset_builder/` (see its package docstring for full detail), not hand-collected or scraped from arbitrary web search results. In summary:

- **Source**: [GBIF](https://www.gbif.org)'s public REST API (`occurrence/search`), which aggregates research-grade, Creative-Commons-licensed photos from iNaturalist and other providers. GBIF's own `robots.txt` permits this; iNaturalist's own API host disallows generic automated query-string access, so this pipeline goes through GBIF rather than around that boundary.
- **robots.txt is enforced at runtime** before every request this pipeline makes — including each image download, which can land on a different host than the API itself — not just checked once by hand.
- **License allowlist**: only CC0/public-domain and CC-BY/BY-SA/BY-NC/BY-NC-SA images are accepted; no-derivatives (ND) licenses are excluded since this pipeline produces derivative works (masks, crops, figures). License and attribution are logged per image to `reports/image_sourcing_log.csv`.
- **Rate-limited and self-identifying**: one request/second by default, with a descriptive `User-Agent` and contact address, and backoff-retry (not hammering) on transient server errors.
- **Human visual review**: automated filters catch mechanical problems (resolution, duplicates) but can't reliably judge "is this a clean, close-up, single-fish photo" — that judgment is made via a generated review page (`reports/review.html`), not by further heuristic tuning.
- **Citation follow-up (open)**: GBIF's own guidance recommends registering a "derived dataset" DOI for data pulled via the search API (as opposed to a bulk download) — this is required before this dataset is cited in any publication, and is tracked as an open action, not yet done.

Full detail, including the reasoning behind each of these choices, is in [CLAUDE.md](CLAUDE.md).

## Planned Approach

1. **Fish identification & extraction** (`src/fish_extractor/`, **complete** — real run finished via [`notebooks/Phase1_Fish_Extraction.ipynb`](notebooks/Phase1_Fish_Extraction.ipynb) on Colab: 856/1,460 images accepted, 604 excluded, 0 flagged) — Grounded SAM 2 (Grounding DINO zero-shot text-prompted detection + SAM 2.1 segmentation) identifies whether an image shows exactly one, roughly-centered fish and, if so, extracts it as a mask-cutout crop. No training required; anything ambiguous was routed to a human-reviewable page rather than silently accepted or dropped, resolved over several review rounds (see the 2.0.0 changelog entry above for the full trail, including the two QA-gate fixes it surfaced).
2. **Pattern extraction** (`src/pattern_extractor/`, **complete** — run via [`notebooks/Phase2_Pattern_Extraction.ipynb`](notebooks/Phase2_Pattern_Extraction.ipynb). The first real run's output was found untrustworthy by a biological sanity check (99% of all 856 images flagged `stripe_present` regardless of species) and stayed unverified through five real, distinct bug fixes — a fixed-pixel noise-filtering floor (v2.0.4), an eccentricity-only elongation check (v2.0.5), an inverted FFT periodicity signal (v2.1.1), a broken RGB colour-dominance check, and a `spot_present` clustering-redesign regression (v2.2.1–v2.2.2) — found via an actual 155-image manually-labeled validation split (`src/pattern_extractor/validation.py`, notebook steps 7/7b), not guessed. Final validated agreement against real hand labels on real SAM2 masks: `is_solid` **70%**, `stripe_present` **81%** (recall ~14%, a deliberately accepted conservative bias — see `StripeConfig`'s docstring, and don't read `stripe_present=False` as a confirmed negative), `spot_present` **80%** (see the 3.0.0 changelog entry for the full trail). Three independent feature extractors run on the fish-extractor's output: coloring (dominant-colour clustering), spots/freckles (connected-component blob shape), stripes (region elongation + per-channel FFT periodicity along the body axes). Kept separate rather than one blended feature vector, because these are developmentally distinct pattern-generating mechanisms (see [BACKGROUND.md](BACKGROUND.md)) — corroborated by the candidate-gene literature review (`data/genes/`), not just an engineering choice. The colour-clustering step is a Python reimplementation of *patternize*'s reference-initialized k-means method (Van Belleghem, S. M., Papa, R., Ortiz-Zuazaga, H., Hendrickx, F., Jiggins, C. D., McMillan, W. O., & Counterman, B. A. (2018, online 2017). patternize: An R package for quantifying colour pattern variation. *Methods in Ecology and Evolution*, 9(2), 390–398. https://doi.org/10.1111/2041-210X.12853), the closest published, peer-reviewed method for this task — demonstrated on fish and used for phylogenetic comparative colour-pattern studies. Two deliberate departures from the original, both because this study compares 64 different species rather than variation within one: no cross-specimen pixel registration (patternize's homology step assumes a broadly consistent body plan), and the stripe/spot geometry analysis is this project's own extension on top of patternize's colour-region output, not a capability patternize itself provides.
3. **Distance matrices** (`src/distance_matrices/`, **complete** — run via [`notebooks/Phase3_Distance_Matrices.ipynb`](notebooks/Phase3_Distance_Matrices.ipynb); real 49-species run verified, see the 4.0.0 changelog entry) — collapses `pattern_extractor`'s per-image feature rows (`reports/pattern_features.csv`) into one per-species vector per pattern dimension, restricted to the 50 species with real genetic-data phylogenetic placement, then builds three species x species pattern-distance matrices (Euclidean on rank-standardized features — see the 3.1.1 changelog entry for why rank, not raw z-score, was needed) plus one patristic-distance matrix from the pruned reference tree, for the secondary Mantel check described below. The circular-hue aggregation concern this step's plan originally anticipated turned out not to apply once the actual feature set was implemented (every `pattern_extractor` output is a non-circular scalar - see the 3.1.0 changelog entry); a real measurement-validity gap the plan *hadn't* anticipated was caught instead - `mean_spot_area` is now normalized by each image's own masked-pixel count before averaging, since raw pixel area isn't comparable across `fish_extractor`'s non-resized crops. **Real per-species counts for the 50-species Kmult set, computed from Phase 1/2's actual output and saved to `data/phylogeny/species_image_counts.csv`:** n=50, total 700 images, mean **14.0**, median 15, range **1–22**. Nothing reached the original 25-image target — Phase 1's real QA gate and human review thinned every species, not just a handful of outliers, so this is a continuous spread across the whole 50-species set rather than a few sparse cases against an otherwise-full baseline. The three most extreme: *Naso maculatus* (**1**, confirmed — its one image *is* the curated reference photo, GBIF sourcing found zero field photos for this species, checked directly against `data/raw_images/Naso/Naso_maculatus.zip`), *Naso tuberosus* (**3**, down from a pre-review 13 — worse than the earlier estimate, not just confirmed by it), and *Acanthurus triostegus* (**5**, an entirely new finding — this species reached the full 25/25 target in Phase 0 but lost 80% of its images during Phase 1's real review). *N. maculatus*'s two-supposedly-independent-decisions-collapse-into-one problem is now resolved in code, not just described: `AggregationConfig.include_reference_images` defaults to False, dropping *N. maculatus* entirely (analysis set n=49, not 50) since its only image is its reference photo; setting it True recovers the species (n=50) as an explicit sensitivity check (notebook step 7), alongside a sparse-species cutoff sensitivity run - both assert their own resulting species count rather than assuming 50.
4. **Statistical test** — **Kmult** (Adams, D. C. (2014). A generalized K statistic for estimating phylogenetic signal from shape and other high-dimensional multivariate data. *Systematic Biology*, 63(5), 685–697. https://doi.org/10.1093/sysbio/syu030) is the primary per-dimension test, run on each pattern dimension's per-species multivariate feature data against the restricted 50-species phylogeny (`data/phylogeny/`). This replaces an earlier plan to use Mantel tests with Harmon & Glor's (2010) phylogenetic-permutation remedy as primary — that remedy specifically targets inflated type-I error in *three-way* Mantel tests, and this project's per-dimension tests are two-way (pattern vs. phylogeny), which Harmon & Glor's own paper says is better served by a K-statistic (Kmult is its multivariate generalization) than by Mantel. **`geomorph::physignal.z()` (not `physignal()`) is the single function planned per dimension**, not two: checked directly against the `geomorph` reference manual, `physignal()`'s own documentation states that as of geomorph 4.0.2 it "no longer reports an effect size" and points users to `physignal.z` for that — and `physignal.z()` already returns everything `physignal()` does (the K statistic itself) plus the optimized branch-scaling parameter (lambda) and the standardized effect size (Z), computed together under one model rather than as two separate analyses that could disagree with no way to reconcile them. `compare.physignal.z` (Collyer, Baken & Adams (2022). A standardized effect size for evaluating and comparing the strength of phylogenetic signal. *Methods in Ecology and Evolution*, 13(2), 367–382. https://doi.org/10.1111/2041-210X.13749) then compares the three dimensions' `physignal.z` results directly — this is the tool for "which pattern dimension carries the most signal," a question three separate p-values can't answer since raw K values aren't on a comparable scale. **Lambda method, preregistered here rather than deferred: `lambda = "front"`, with one shared `PAC.no` value applied across all three pattern dimensions** (not chosen post hoc, and not a per-dimension value, even though the three feature matrices differ in width). This matches the `geomorph` manual's own `compare.physignal.z` worked example exactly — it calls `physignal.z(..., lambda = "front", PAC.no = 7)` identically for both traits being compared, before comparing them — the package authors' demonstrated usage for precisely this "compare signal across trait subsets on one tree" case. `"front"` was chosen over the other three documented options for a specific reason tied to this project's history: `"burn"` explicitly "sample[s] a spectrum of lambda from 0 to 1... to find the lambda value that maximizes the effect size rather than the log-likelihood" — but Z, the effect size, is exactly what `compare.physignal.z` compares across the three dimensions, so using `"burn"` would mean comparing three separately-maximized quantities, a shape of risk this project has already been burned by once (the pre-rebuild pipeline's data-dredged phylogenetic-signal result). `"all"` "will tend to optimize lambda at 0 or 1," which is precisely the documented `NaN`-Z failure case already guarded against above, so it carries the highest exposure to that failure mode. `"front"`'s own documented cost: it "will tend to bias lambda toward 1, making analysis more similar to using multivariate K, as in physignal" — a real limitation to carry forward, not a free choice. `PAC.no` itself will be chosen from the most data-constrained of the three feature matrices and reported (per-dimension component counts recorded alongside), since `PAC.no` sets the dimensionality that Z's underlying log-likelihood is estimated in, and comparing Z values estimated at different dimensionalities would need its own justification the manual doesn't provide. **Seed handling**: `physignal.z`'s `seed` argument defaults to `NULL`, which the manual states gives "the exact same P-values... for repeated runs" — that deterministic default will be used (not `seed = "random"`), consistent with this project's other reproducibility measures (the pinned tree checksum, the saved synonym table). (`physignal()` at full, untransformed-tree dimensionality may still be run as an optional, explicitly-labeled unit-tree sensitivity check alongside the primary `physignal.z` result, not as a second primary result.) The three pairwise-distance Mantel tests (one per pattern dimension, phylogenetically-permuted) are retained as a **secondary**, distance-based check. A multiple-comparisons correction across the three dimensions applies to both the primary `physignal.z` results and the secondary Mantel results before anything is called significant. Under either test, a null result is reported as inconclusive, not as evidence of no association — Harmon & Glor found the Mantel test has real power limitations even with the correct remedy applied.
   - **Why not `physignal.eigen`**: also part of `geomorph` (Mitteroecker, Collyer & Adams 2024), it decomposes *where within one feature matrix* phylogenetic signal concentrates (which dimensions of that matrix carry it) — a different question from this project's actual one, which is comparing signal strength *across* three separate feature matrices (color vs. stripe vs. spot). `compare.physignal.z` is the right tool for that comparison; `physignal.eigen` was considered and isn't a substitute for it, though it could be a useful follow-up if a single dimension turns out to carry most of the signal and *which features within it* becomes the next question.
   - **Data-admissibility note, not just implementation detail**: every `physignal`/`physignal.z` argument in the `geomorph` manual is documented in terms of "Procrustes shape variables" from Generalized Procrustes Analysis — the package's default assumption is shape data, and Adams (2014)'s title phrase ("shape and *other* high-dimensional multivariate data") is the sole basis for using it on this project's non-shape colour/stripe/spot features. That makes the log-ratio transform, standardization, and condition-number check below **admissibility requirements for using a shape-signal method on non-shape data**, not routine data hygiene — skipping them isn't just sloppy, it's applying the method outside where its own documentation says it's been shown to work.
   - **Implementation language, revised**: `physignal.z`/`compare.physignal.z` are not simple formulas to port — per the `geomorph` manual they involve phylogenetically-aligned component projection, likelihood optimization of the branch-length scaling parameter, RRPP-based permutation, and a Box-Cox standardized effect size, and this project has already shipped one silently-wrong metric (the pre-rebuild pipeline's misreported ROC-AUC). An "almost right" hand port returns a plausible, wrong number with no visible error. Preferred approach: run these specific statistics in R (via `rpy2` or as a documented standalone R step Python hands the pruned tree and feature matrices to) rather than reimplementing them — the feature matrices are small (50 x p), so there's no performance case for a Python port here the way there was for `pattern_extractor`'s per-pixel clustering. If a Python port is done anyway, it is gated on a numerical-equivalence test: run `physignal.z`/`compare.physignal.z` on `geomorph`'s own `plethspecies` example dataset (confirmed present in the package, used in the manual's own examples for both functions) in R, commit the output, and require the port to reproduce it to a stated tolerance as a unit test before it's trusted on real data — the same gap applies to the *patternize* colour-clustering reimplementation already in `pattern_extractor` (no equivalence check against the R package exists yet), tracked as a follow-up, not blocking Phase 2's existing prototype status.
   - **Feature-matrix requirements for Kmult**, to satisfy before running (binding fast at n=50, not yet built): compositional features (e.g. colour proportions summing to 1) need a log-ratio transform (CLR/ILR) since raw proportions make the covariance matrix singular; mixed-unit features need standardization; dimensionality must stay well under n=50 with the reduction choice reported, not defaulted silently; a rank/condition-number check on each dimension's feature matrix must fail loudly on ill-conditioned input rather than silently returning a number. Watch for `physignal.z` returning `NaN` when the phylogenetic scaling parameter optimizes to 0 — the `geomorph` manual itself says the standard error is also 0 in that case and pairwise comparisons "might not make sense."
   - **Tree and matching integrity checks**, not yet built: assert the loaded tree's tip count falls in a range that discriminates the genetic-data-only tree from the much larger "complete" tree (e.g. `10,000 < ntip < 15,000`, with both candidate counts — 11,638 genetic-data tips vs. 31,526 complete-tree tips, both from Rabosky et al. 2018 — named in a comment) rather than an exact `== 11638` check, which would break on any release that differs by even one tip; prune to the 50 study species *before* computing any patristic-distance/cophenetic matrix, not after (the unpruned matrix is ~1.08 GB as float64 vs. ~20 KB pruned); and assert that feature-matrix row order matches the pruned tree's tip-label order, failing loudly on mismatch — `geomorph` matches by name, and a Python port will match by array position unless written not to, which would produce a well-formed, meaningless result on any accidental reordering.
   - Species-count integrity: `assert matched == 50` (or equivalent) when loading `species_coverage.csv`, so a drift in the matched count is a loud failure, not a silently stale number.
5. **(Contingent, deferred)** If any pattern dimension shows a significant, corrected result: investigate whether the 56 candidate genes identified in the literature review (`data/genes/`) are present/annotated in the genome assemblies available for 16 of the 64 species (`data/genome_assemblies/`), and whether any expression data can be found. Not yet scoped in detail.
