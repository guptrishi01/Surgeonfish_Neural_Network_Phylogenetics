# Changelog

Full version history for the Surgeonfish Visual Phenomics and Phylogenetic
Inference project. See [README.md](README.md) for the results and pipeline
overview, and [METHODS.md](METHODS.md) for the statistical design rationale.

Versioning scheme (see [CLAUDE.md](CLAUDE.md)): **major** = a rebuild phase
completed, **minor** = a discrete step within a phase, **patch** = a bug fix.

This history is deliberately detailed. Most entries record a bug found by
checking real output against something known to be true, and several record
a plan being corrected against reality rather than followed off a cliff --
that trail is a substantial part of what makes the final numbers
trustworthy, so it is kept rather than summarised away.

- **6.5.0** — **The *patternize* port is validated — the project's largest unquantified risk is closed.** `pattern_extractor`'s colour clustering is a Python reimplementation of *patternize*'s reference-initialised k-means that had never been checked against the R package, sitting directly upstream of the only significant result. Running both on identical pixel sets from identical starting centres gives a worst disagreement of **0.0037** across 12 cluster fractions on three species spanning the pattern range (*A. lineatus* 0.0027, *C. striatus* 0.0037, *Z. flavescens* 0.0034) — against a **0.05 threshold stated before the run**, so this is not a post-hoc reading. Differences at that scale are what two independent k-means implementations produce through convergence details, not a porting bug. Saved to `outputs/patternize_check/equivalence_result.csv`. **The check had to be fixed twice, and that is the more instructive part.** The first version compared the two implementations on the same crop and reported differences of 0.11–0.26, a number alarming enough to read as a real problem — but it established nothing, because `kImage()` clusters the entire raster including the mask cutout's grey background while `pattern_extractor` clusters masked-in pixels only, so the two were partitioning different pixel sets. Rebuilding the inputs to contain only masked-in pixels dropped the worst disagreement from **0.2638 to 0.0037**, a ~70× change produced entirely by fixing the measurement rather than the code under test. A second, subtler failure followed: re-running in Colab appeared to reproduce the old confounded numbers exactly, which turned out to be the stale notebook cell in the browser regenerating full-crop PNGs over the committed strips — diagnosed by checking image dimensions (500px strips vs full crops) rather than assuming the pull had failed. Both are worth recording: an instrument can be wrong in a way that looks exactly like a finding, and this project has now been bitten by that in both directions. With this closed, four of the five open follow-ups are done and the fifth (GBIF registration) is deliberately skipped as inapplicable to unpublished work. 206 tests passing, ruff clean.
- **6.4.0** — Fixed the *patternize* equivalence check so it can actually answer the question, and recorded that the GBIF registration is deliberately not being done. **The check was confounded, and the fix removes the confound rather than adjusting for it.** v6.3.0's attempt compared `patternize::kImage()` against our clustering on the same crop and found cluster fractions differing by 0.11-0.26 - a number that established nothing, because `kImage()` clusters the entire raster including the mask cutout's grey background while `pattern_extractor` clusters masked-in pixels only. The two were partitioning different pixel sets, so neither agreement nor disagreement would have meant anything. New `scripts/make_patternize_inputs.py` emits, per test image, a PNG containing **only the masked-in pixels** reshaped into a rectangle: no background exists for one implementation to include and the other to exclude, so both cluster an identical pixel multiset from an identical `startCenter` matrix. At most 0.45% of pixels are dropped to make the count rectangular (470, 349 and 133 pixels on the three test images), reported per image in `outputs/patternize_check/python_reference.csv` rather than silently absorbed. Three species were chosen to span the pattern range - strongly striped *A. lineatus*, plain *Z. flavescens*, mid-case *C. striatus* - so the comparison isn't made on one convenient image. The R side additionally checks the raster's value range before clustering and rescales the starting centres if the reader returns 0-1 rather than 0-255, instead of assuming either. **Not yet run**, so the port remains unvalidated rather than invalidated - but with the confound gone, whatever number comes back is a genuine algorithmic comparison, where small differences are expected from k-means convergence and a large disagreement would indicate a real porting bug. **GBIF registration deliberately skipped.** GBIF's data user agreement asks for a DOI citation when data is used in research or policy; this project is exploratory work that is not being published, so the trigger does not apply. The derived-dataset table stays committed and ready should that change, and the README no longer describes it as a publication blocker. 206 tests passing, ruff clean.

- **6.2.0** — Recalibrated stripe detection against the **real SAM 2 masks**, and found a second, unrelated problem while checking the result. Both came from finally having `data/extracted_fish/` available locally, which had never been possible before. **(1) The v2.2.3 conclusion that stripe recall could not be improved was wrong — it was an artifact of approximated masks.** That calibration used a corner flood-fill approximation and said so, with an explicit "re-check against production" caveat that was never closed. Closing it overturns the conclusion: re-running the same grid against the same 155 hand labels, now with real masks, shipped thresholds (eccentricity 0.97 / count 20 / width 0.12) give precision 40.0% / recall 14.3% / F1 0.211, while (0.98 / **8** / 0.10) give precision 40.0% / recall **50.0%** / F1 **0.444** — recall triples at *identical* precision. The chosen values are the consensus of **200 stratified split-half trials** (thresholds selected on one half, scored on the held-out half), not the single F1-maximising point on the full set, specifically to avoid selecting on the data and then reporting performance on it; held-out F1 goes 0.200 → 0.336, with the re-tuned settings winning in 93.5% of trials, and the median selected count threshold was 8 (IQR 6–10) against the shipped 20. Approximated masks produce far more spurious elongated regions than real ones, which is why a bar of 20 looked necessary and is in fact far too high. **The periodicity signal was also re-checked on real masks and is confirmed dead** — correlation with the hand labels is r=+0.020 / −0.092 / −0.066 at cycles 2/3/4, indistinguishable from noise and two of three pointing the wrong way; that was previously flagged as "needs re-validation, not concluded dead," and is now concluded. **(2) `spot_present` is effectively non-functional, and had been reported as a success.** Checking all three detectors against the labels on real masks gives `is_solid` F1 0.775, `stripe_present` F1 0.444, and `spot_present` F1 **0.114** — precision 10.5%, recall 12.5%, **2 true positives against 17 false positives across 155 images**. Its 80% "agreement", quoted in the README as a validated number since v2.2.3, is pure class-imbalance artifact: it has the *highest* agreement of the three detectors and is by far the worst. This is exactly the failure mode this project has hit repeatedly (the 99%-stripe bug, the 41% `is_solid` bug) — an aggregate metric concealing a broken detector — and it survived because v2.2.2's precision/recall figures came from the approximate-mask calibration and only the aggregate was ever confirmed on real data. Importantly it does **not** invalidate the spot dimension: `prop_spotted` is one of ten per-species features, the dimension's signal comes from the continuous `mean_spot_count`/`mean_spot_area_fraction`, and dropping the thresholded proportions entirely *strengthens* spot's Mantel result (BH p 0.030 → 0.017) rather than weakening it. README now carries a detector-quality table with F1 and true-positive counts, and says plainly to read F1 rather than agreement. **Downstream re-run.** Phases 2 and 3 were re-run locally against the real crops (853 rows, unchanged count; `is_solid` and `spot_present` bit-identical before and after, confirming the change was surgical; `stripe_present` fires on 23.0% of images versus 7.2%, against an 18% true rate in the labelled sample). Also closed two other follow-ups: **the *Zebrasoma veliferum* synonym is confirmed against a real fish taxonomic authority** (FishBase gives *Zebrasoma velifer* (Bloch, 1795), Acanthuridae — the project's canonical label uses the *veliferum* spelling, a nomenclatural convention difference, not an identity error), and **the redundant thresholded proportions were tested and don't matter** (dropping `prop_solid`/`prop_striped`/`prop_spotted` leaves every verdict unchanged). - **4.2.1** — Real bug, found on the first real execution of v4.2.0's Mantel check: every dimension came back with a near-1.0 p-value (color 0.998, stripe 0.999, spot 0.998), regardless of the fact that Kmult had already found color's signal genuinely significant — a degenerate result, not a real finding. Root cause was a design flaw, not a coding mistake: v4.2.0's null was built by simulating traits under Brownian motion on the real tree, but BM trait divergence is *by definition* proportional to patristic distance, so that "null" was actually closer to the theoretical ceiling of possible phylogenetic correlation than to "no association" — real, noisy biological data will almost always look weaker than a pure BM simulation, biasing every dimension toward non-significance regardless of the truth. Found by re-reading this project's *own* already-verified README finding on exactly this point (Phase 4's Context section, checked against Harmon & Glor's actual abstract in an earlier audit round): their phylogenetic-permutation remedy specifically targets *three-way* Mantel tests (two independently-measured, both phylogenetically-confounded matrices compared to each other) — this project's test is *two-way* (one measured pattern-distance matrix against the fixed, exactly-known patristic matrix), which the same paper says is better served by a K-statistic (Kmult, already the primary test) than by Mantel at all. Replaced the BM-simulation null with standard label-permutation Mantel (shuffle one matrix's species order relative to the fixed patristic reference, recompute the correlation, 1,000 times) — a legitimate, well-understood null for exactly this fixed-reference two-way case, using nothing beyond base R. Carries the ordinary Mantel-test caveats only, not the phylogenetically-inflated-type-I-error risk that doesn't actually apply to this project's design. **Not yet re-executed** — same checkpoint as before, this needs a real run before Phase 4 can be called complete.
- **4.2.0** — Added the secondary phylogenetically-permuted Mantel check (Harmon & Glor 2010) to `r/phase4_kmult.R` (Steps 6-8), the piece deliberately deferred out of v4.1.0. Per Harmon & Glor, naive label-shuffling permutation inflates Mantel's type-I error when both matrices carry phylogenetic autocorrelation — their remedy is to build the null distribution by simulating trait evolution *on the real tree* (Brownian motion) instead of permuting species labels. Implemented using `ape::rTraitCont()` — its real signature (`phy`, `model`, `sigma`, `root.value`, ...) checked against the CRAN manual before writing any code depending on it, per the anti-guessing rule v4.1.1 just added to CLAUDE.md — plus base R (`cor()`/`lower.tri()`/`dist()`) for the Mantel statistic itself, deliberately not another unfamiliar package's Mantel implementation (e.g. `vegan::mantel()`), to keep the number of unverified API surfaces in one round as small as possible.
